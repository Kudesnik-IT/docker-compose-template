# Проектная структура и инструкция по запуску

Этот репозиторий использует масштабируемую и интуитивно понятную структуру проекта Docker.

Основная цель — **простота, ясность и готовность к росту**, без излишней сложности на старте.

## 🧩 Почему именно такая структура?

### 🔹 1. Простота и соответствие стандартам

- **`compose.yaml` и `.env` в корне** — это **официальное поведение Docker Compose по умолчанию**.
- Нет необходимости указывать `-f` или пути — всё работает "из коробки".
- Новички сразу понимают, где основная конфигурация.

> 💡 Это соответствует принципу **"convention over configuration"**.

---

### 🔹 2. Чёткое назначение каждой директории

| Папка | Назначение |
|------|-----------|
| **`compose.yaml`** | Главный файл оркестрации. Определяет сервисы, сети, тома. Должен быть в корне — так Docker Compose находит его автоматически. |
| **`.env`** | Общие переменные окружения, используемые **только для подстановки в `compose.yaml`** (например, `PORT_SERVICE`, `COMPOSE_PROJECT_NAME`). Не попадает в контейнеры, если не указано явно. |
| **`apps/`** | Исходный код всех сервисов. Каждый сервис — в своей подпапке. Это позволяет легко масштабировать проект и при необходимости вынести сервис в отдельный репозиторий. |
| **`config/`** | Внешние конфигурационные файлы для сервисов: `nginx.conf`, скрипты инициализации БД и т.д. Не часть кода, но необходимы для запуска. |
| **`data/`** | Всё, что создаётся в рантайме: логи, загруженные файлы, данные БД. <br> ❗ Не коммитится в Git. <br> ✅ Упрощает бэкапы и отладку. |
| **`docker/`** | Всё, что относится к Docker, кроме основного `compose.yaml`. <br> • `compose.dev.yaml`, `compose.prod.yaml` — override-файлы для разных окружений. <br> • `docker/.env/` — централизованное хранение env-файлов, **не попадающих в основной `.env`**. <br> Такая структура не засоряет корень и соответствует 12-Factor App. |
| **`docker/.env/environments/`** | Переменные, специфичные для окружения: `.env.dev`, `.env.prod`. <br> Используются через `--env-file` для переопределения `.env`, но **не попадают в контейнеры**, если не указаны явно в `environment` или `env_file` сервиса. |
| **`docker/.env/services/`** | Переменные, специфичные для **конкретного сервиса** (например, `sample.env`). <br> Передаются в контейнер через `env_file` — только те, что нужны приложению. |
| **`scripts/`** | Вспомогательные скрипты: деплой, бэкап, миграции. |
| **`tests/`** | Тестовые конфигурации, например, `compose.test.yaml` с упрощённой сетью и временными контейнерами. |
| **`.dockerignore`** | Запрещает попадание в контекст сборки лишних файлов: `.env`, `node_modules`, `data/` и т.д. Критически важен для безопасности и скорости сборки. |
| **`.gitignore`** | Исключает из репозитория: `.env`, `data/`, `docker/.env/*`, `logs/` — всё, что не должно быть в Git. |
| **`Makefile`** | Упрощает работу с Docker Compose. Позволяет запускать `make dev` вместо длинных команд. |

---

### 🔹 3. Почему `.env` в корне?

- Docker Compose **автоматически ищет `.env` в той же директории, что и `compose.yaml`**.
- Это **стандартное и ожидаемое поведение**.
- Упрощает onboarding: разработчик видит `.env` — понимает, где настройки.

> ⚠️ `.env` — содержит значения по умолчанию, безопасные для коммита.

---

### 🔹 4. Где хранятся переменные окружения для сервисов и окружений?

Все **чувствительные и специфичные переменные** хранятся в `docker/.env/`, структурированно:

```markdown
docker/.env/
│                  # Переменные для разных окружений
├── .env.dev       # Для разработки
├── .env.prod      # Для продакшена
│
└── services/      # Переменные для конкретных сервисов
    └── sample.env # Например, для сервиса sample
```

> 🔐 Ни один из этих файлов **не коммитится в Git** (указаны в `.gitignore`).

Такой подход:
- Соответствует политике: конфигурация хранится в переменных окружения, а не в коде
- Разделяет **инфраструктурную конфигурацию** (`.env`, `.env.dev`) и **прикладную** (`sample.env`)
- Позволяет гибко комбинировать окружения и сервисы

---

### 🔹 5. Почему override-файлы в `docker/`?

- Основной `compose.yaml` — в корне, как и положено.
- Все **дополнительные конфигурации** (`dev`, `prod`, `test`) — в `docker/`.
- Это **не засоряет корень**, но при этом всё остаётся структурированно.

> 📌 Пример: `docker/compose.dev.yaml` добавляет:
> - автоперезагрузку
> - отладочные порты
> - `.env.dev` через `env_file`

---

### 🔹 6. Управление окружениями и сервисами

Мы используем **модульную систему переменных**:

| Файл | Назначение | Коммитится? |
|------|-----------|------------|
| `.env` (в корне) | Общие переменные по умолчанию | ✅ Да |
| `docker/.env/environments/.env.dev` | Dev-специфичные переменные | ❌ Нет |
| `docker/.env/environments/.env.prod` | Prod-специфичные переменные | ❌ Нет |
| `docker/.env/services/sample.env` | Переменные для сервиса `sample` | ❌ Нет |
| `docker/.env/.env.example` | Шаблон для новых разработчиков | ✅ Да |

> 🔐 Секреты (пароли, ключи API) — только в файлах в `docker/.env/`.  
> `.env.example` содержит только шаблоны: `DB_PASSWORD=your_password_here`.

## 🛠️ Механизм запуска

### 📦 Управление через `Makefile`

Для упрощения используются короткие команды:

```makefile
.PHONY: up down dev prod test logs

# Запуск базовой конфигурации (без override)
up:
	docker compose up -d

# Остановка
down:
	docker compose down

# Запуск в режиме разработки
dev:
	docker compose \
		--env-file .env \
		--env-file docker/.env/environments/.env.dev \
		-f compose.yaml \
		-f docker/compose.dev.yaml \
		up -d --build

# Запуск в продакшене
prod:
	docker compose \
		--env-file .env \
		--env-file docker/.env/environments/.env.prod \
		-f compose.yaml \
		-f docker/compose.prod.yaml \
		up -d --build

# Запуск тестов
test:
	docker compose \
		--env-file .env \
		-f compose.yaml \
		-f tests/compose.test.yaml \
		up --abort-on-container-exit

# Просмотр логов
logs:
	docker compose logs -f
```

## 🔄 Как работают override-файлы?

### `docker/compose.dev.yaml`
- Подключает `.env.dev` через `env_file` → переопределяет значения из `.env`
- Включает `volumes` для автоперезагрузки кода
- Открывает порты для отладки
- Использует `restart: unless-stopped`

### `docker/compose.prod.yaml`
- Подключает `.env.prod`
- Отключает лишние порты
- Использует `restart: always`
- Может включать лимиты памяти, HTTPS, healthcheck

## 📝 Как начать работу?

### 1. Склонируйте репозиторий
```bash
git clone https://github.com/your/project.git
cd project
```

### 2. Настройте переменные окружения
```bash
cp docker/.env/.env.example docker/.env/.env.dev
# Отредактируйте .env и docker/.env/.env.dev
```

### 3. Запустите в режиме разработки
```bash
make dev
```

### 4. Проверьте логи
```bash
make logs
```

### 5. Остановите
```bash
make down
```

## ✅ Преимущества этой структуры

| Преимущество | Реализация |
|------------|-----------|
| **Простота** | `.env` и `compose.yaml` в корне — как в туториалах |
| **Масштабируемость** | Легко добавить новые override-файлы |
| **Читаемость** | Чёткое разделение: код, конфиги, данные |
| **Безопасность** | Секреты — только в `.env.dev` / `.env.prod` |
| **CI/CD-дружелюбность** | Работает с `docker compose -f ...` без костылей |
| **Готовность к росту** | Можно вынести `apps/backend/` в отдельный репозиторий |

## 📚 Рекомендации

- Никогда не коммитьте `.env, `.env.dev`, `.env.prod`, `sample.env`
- Обновляйте `.env.example` при добавлении новых переменных
- Используйте `make dev`, `make prod` — не пишите длинные `docker compose` вручную
- Регулярно бэкапьте папку `data/`
- Для новых сервисов: создайте папку в `apps/` и `.env`-файл в `docker/.env/services/`
